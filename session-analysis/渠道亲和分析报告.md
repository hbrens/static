# New API 渠道亲和（Channel Affinity）能力分析报告

> 分析目标：确认 New API v0.11.5 能否为 ZCode 配置「会话级」渠道亲和；若不能，缺口在哪、从哪个版本开始可用。
> 分析日期：2026-09-15
> 分析方式：源码审读（v0.11.5 tag + main 分支）+ 容器实测 + 中间代理流量取证 + 上游 issue/PR/release 追溯

---

## 开篇：渠道亲和对自部署模型多实例部署的意义

### 为什么自部署模型会变成「多实例 + 网关」

自己部署模型时，单实例几乎必然会成为瓶颈：显存装不下更大的模型、单卡的并发和吞吐有上限、扩缩容需要横向加机器。于是常见的形态就变成：

```
                        ┌── 实例 A（vLLM / SGLang / llama.cpp / Ollama …）
  客户端 → New API 网关 ─┼── 实例 B
                        └── 实例 C
```

这些实例对网关而言就是**同一模型的多个渠道**（可能同分组、同优先级、同权重），网关按轮询 / 加权随机 / 优先级把请求分发出去。

**问题就出在这个「分发」上：它默认是逐请求、无记忆的。**

### 没有亲和时会发生什么

同一轮对话（同一个 Agent 会话、同一个长上下文任务）的多个请求，会被**独立地**随机打到不同实例。由此产生三类代价：

| 代价 | 原因 |
|---|---|
| **前缀缓存失效，TTFT 与算力被浪费** | 自部署推理引擎的 KV 缓存是**每实例独立**的（vLLM 的 automatic prefix caching、SGLang 的 RadixAttention 等）。同一会话的 prompt 前缀高度重复，本可整段命中；一旦被轮询到别的实例，前缀缓存全丢，整段 prefill 重算一遍 |
| **会话行为漂移，排障困难** | 不同实例的量化版本、采样实现、加载的 adapter、并发压力都可能不同，同一会话在不同实例上表现可能不一致；排查时也无法把问题定位到单一实例 |
| **上游侧缓存同样失效** | 若渠道指向的是各家云 API 而非自建实例，prompt caching / context caching 也多为**按账号或按实例**计费与命中，切换渠道等于重新计费 |

对话越长、Agent 工具调用越密，这三类代价被放大的倍数越高 —— 一个编码 Agent 会话往往几十轮，每轮都携带数万 token 的积累上下文，逐轮命中不同实例意味着**反复重算同一段前缀**。

### 亲和带来什么

渠道亲和（Channel Affinity）本质是给网关加一层**「成功渠道记忆」**：首次成功命中某渠道后，网关以请求中的某个标识生成缓存键，把「标识 → 渠道」记下来；后续携带同一标识、且模型与分组等条件匹配的请求，**优先复用该渠道**。

落到自部署多实例场景，收益是直接的：

1. **保住前缀缓存** —— 同一会话固定落同一实例，KV 前缀整段复用，首 token 延迟和 prefill 算力显著下降。这是最主要的价值。
2. **会话行为一致** —— 同一会话的每轮都由同一实例处理，避免实例间实现差异带来的抖动。
3. **排障可定位** —— 命中情况会写进请求日志（`channel_affinity` 字段，含 `rule_name` / `key_fp` / `channel_id`），可按会话追溯到底走了哪个实例。
4. **多实例（或多上游账号）之间可做稳定分区** —— 用 `include_using_group` 等作用域开关让不同分组、不同调用方各自粘住各自实例，而不必依赖随机均衡。

### 代价与权衡（不是白拿的）

亲和是**软优先 + 有状态**的，代价必须一起接受：

- **调度变更不会立刻生效**：新增实例、调整权重或优先级后，已有亲和缓存里的会话仍会走旧实例，直到 TTL 到期或缓存被清空。
- **实例故障可能「粘住」**：需配合 TTL 调优与 `skip_retry_on_failure`（失败后是否允许切换并覆盖缓存）、以及新版的 `keep_on_channel_disabled`（渠道被禁用时是否保留亲和缓存）来平衡稳定性与故障切换速度。
- **负载可能不均**：热点会话会把压力集中在个别实例上，亲和越强越明显。它是**稳定性**的收益，不是**均衡性**的收益。
- **必须有一个稳定的会话标识**：这是全部前提。标识要么客户端给（`prompt_cache_key` / `metadata.user_id` / 自定义请求头），要么用网关侧的内部键（`token_id` 等，粒度只能到令牌级）。**标识不稳，亲和就是随机**。

### 由此引出本报告的问题

上面最后一条正是本次分析的起点：

- Claude Code 把会话标识放在请求体的 `metadata.user_id`
- Codex CLI 放在请求体的 `prompt_cache_key`
- **ZCode 只放在请求头 `x-session-id`**

而 New API **v0.11.5** 可用的 Key 来源只有 `context_int` / `context_string` / `gjson` 三种 —— 其中唯一能读到客户端自定义标识的 `gjson` **只读请求体**。于是 ZCode 这类「只在 header 带会话标识」的 Agent，在 v0.11.5 上**拿不到会话级亲和**，前缀缓存的收益也就落不到它头上。

后面各节逐步验证这个结论，并给出可落地的方案。

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| v0.11.5 能否为 ZCode 配置会话级渠道亲和？ | **不能**。三种 Key 来源（`context_int` / `context_string` / `gjson`）都读不到请求头 |
| ZCode 的会话标识在哪？ | **只在请求头** `x-session-id`，请求体里没有 |
| 其他 Agent 为什么能用？ | Claude Code 和 Codex CLI 都把会话标识**同时放进了请求体**，所以 `gjson` 够得着 |
| 「通过请求头做亲和」是新功能吗？ | **是**。`request_header` 类型由 PR #4903 引入，随 **v1.0.0-rc.7（2026-05-19）** 发布，比 v0.11.5 晚约 2 个月（官方 Release / PR / Issue / 第三方博客四类来源互证，见 §10） |
| 当前常驻实例支持吗？ | **支持**。常驻实例为 `v1.0.0-rc.25`，前端已含 `request_header` |
| 不改代码能补救吗？ | 不能。`param_override`/同步字段把 header 写进 body 无效——Key 提取发生在原始请求体上，早于参数覆盖（上游 Issue #4896 报告者已实测确认） |

一句话：**v0.11.5 唯一的「客户端自定义标识」通道是 `gjson`（只读 body）；ZCode 把标识放在 header，所以命中不了。该缺口由 v1.0.0-rc.7 的 `request_header` 补齐。**

> 结论的验证方式：源码审读 + 容器实测 + 流量取证 + 联网佐证，四条线互相独立。网络佐证的逐条核对见 §10。

### 2.3 是否存在隐藏规则

**没有。** 全仓 `ChannelAffinityRule` 的定义处只有 `channel_affinity_setting.go` 一个文件；`middleware/distributor.go` 中仅 3 处调用（`:102` 取亲和渠道、`:113/:120` 标记命中、`:157` 成功后回写），无任何硬编码的隐式命中逻辑。

前端另有一份等价常量 `web/src/constants/channel-affinity-template.constants.js:62-87`（`CHANNEL_AFFINITY_RULE_TEMPLATES`），与后端两条默认规则内容一致，仅用于「填充模版」按钮（`SettingsChannelAffinity.jsx:446`）。

### 2.4 匹配与生效流程

匹配是 4 个条件的与门（`service/channel_affinity.go:547-570`）：

```
model_regex 匹配 model
  → path_regex 匹配 path
    → user_agent_include 子串匹配 UA（忽略大小写）
      → 按 key_sources 顺序取第一个非空值
        → （可选）value_regex 校验该值
```

生效为**软优先**，非硬绑定：

- `middleware/distributor.go:102` — 命中则取缓存渠道，且要求渠道状态为 enabled、对当前分组模型可用
- `distributor.go:125` — 未命中或渠道不可用则回落 `CacheGetRandomSatisfiedChannel` 随机调度
- `distributor.go:157` — 请求成功后（`status < 400`）回写亲和缓存
- `service/channel_affinity.go:660-687` — `RecordChannelAffinity` 写入，`switch_on_success=true` 时以实际成功渠道覆盖

### 2.5 配置持久化行为（一个易踩的坑）

`setting/config/config.go:255-261` 对复杂类型（切片/Map/结构体）直接 `json.Unmarshal` 到字段上：

```go
case reflect.Map, reflect.Slice, reflect.Struct:
	err := json.Unmarshal([]byte(strValue), field.Addr().Interface())
```

即 `rules` 是**整体替换**，不与代码里的默认值合并。

实测验证：v0.11.5 全新实例的 `options` 表中**不存在**任何 `channel_affinity_setting.*` 键 —— 默认值只存在于代码中。一旦管理员在设置页保存过（哪怕是空数组），代码里的两条默认规则即永久失效，不会自动恢复。

## 3. Key 来源三种类型的能力边界

取值实现：`service/channel_affinity.go:279-320`

```go
func extractChannelAffinityValue(c *gin.Context, src operation_setting.ChannelAffinityKeySource) string {
	switch src.Type {
	case "context_int":
		if src.Key == "" { return "" }
		v := c.GetInt(src.Key)
		if v <= 0 { return "" }
		return strconv.Itoa(v)
	case "context_string":
		if src.Key == "" { return "" }
		return strings.TrimSpace(c.GetString(src.Key))
	case "gjson":
		if src.Path == "" { return "" }
		storage, err := common.GetBodyStorage(c)
		if err != nil { return "" }
		body, err := storage.Bytes()
		...
		res := gjson.GetBytes(body, src.Path)
		...
	default:
		return ""
	}
}
```

| 类型 | 数据来源 | 能否读到客户端自定义标识 |
|---|---|---|
| `gjson` | **原始请求体**（`common.GetBodyStorage`） | ✅ 能（前提是客户端把标识放 body） |
| `context_int` | gin context 中的 int 键 | ❌ 只读服务端内部状态 |
| `context_string` | gin context 中的 string 键 | ❌ 只读服务端内部状态 |

**关键点：`context_int` / `context_string` 读的不是客户端传来的东西。** 它们读的是服务端内部键。

`constant/context_key.go` 全量 60+ 个 key 中，与客户端最接近的是：

```
token_id / token_key / token_group / group / id / username / user_group / user_email / specific_channel_id
```

全部是**令牌级或用户级**，无一是「会话级」，也没有任何一个是请求头派生的。唯一名字含 header 的 `ContextKeyChannelHeaderOverride`（`= "header_override"`）是**渠道自身的 header 覆盖配置**，且写入位置（`distributor.go:357`）晚于亲和判定（`:102`），不可用。

### 3.1 已知的死路：用「同步字段」把 header 写进 body

思路是把客户端 header 通过「同步字段」注入请求体，再用 `gjson` 读取。**此路不通**，原因在调用顺序：

- `middleware/distributor.go:102` → 取亲和（读原始 body）
- `middleware/distributor.go:353` → `ApplyChannelAffinityOverrideTemplate` 才应用参数覆盖

亲和判定发生在参数覆盖之前，参数覆盖生成的内容对亲和不可见。上游 Issue #4896 的报告者也实测确认了这一点。

| `[3]` | user | 可变 | 用户首条输入 | 会话内不变，跨会话通常不同 |
| `[4..]` | 混合 | 增长 | 对话过程 | 逐轮变化 |

**会话标识只在 header：**

```
x-session-id        09fe0e7d-8d7c-4db3-8e1c-9afa48e92721   (11 条)
                    6957f757-…                              (1 条)
x-zcode-trace-id    2e02d3d2-78c2-4721-9dba-0654c6d9461d
x-request-id        04542202-c30b-461e-9c54-4d6396a49570
x-zcode-agent       glm
x-zcode-app-version 3.11.2
x-zcode-session-type main
```

同时确认：body 中**不存在** `user`、`metadata`、`prompt_cache_key` 字段。

### 4.4 对照汇总

| 客户端 | body 中的会话标识 | 能否被 v0.11.5 的 `gjson` 取到 |
|---|---|---|
| Claude Code | `metadata.user_id` → `{"session_id":"…"}` | ✅ |
| Codex CLI | `prompt_cache_key`（= session id） | ✅ |
| ZCode | **无** | ❌ |

## 5. 结论：v0.11.5 为什么配不出 ZCode 的会话亲和

准确表述不是「v0.11.5 只支持 body」，而是：

> **v0.11.5 的三种 Key 来源里，唯一能读到「客户端自定义字段」的通道是 `gjson`，而 `gjson` 只读请求体。另外两种读的是服务端内部状态（`token_id` / `username` / `group` 等），与客户端传入的内容无关。**

因此，**会话级亲和能否实现，完全取决于客户端把会话标识放在请求体还是请求头**。这解释了为什么内置的两条默认规则恰好在 Claude Code 和 Codex CLI 上生效 —— 这两个客户端都主动把会话标识放进了 body，而且用的是有明确上游语义的字段（`metadata.user_id` / `prompt_cache_key`）。

ZCode（以及 OpenCode 等）只在 header 带会话标识，v0.11.5 就无法覆盖。

### 5.1 已被排除的替代方案

| 方案 | 为什么不行 |
|---|---|
| `context_int: token_id` | 令牌级而非会话级；且 UI 本就提供该选项，等于没解决 |
| `context_string: username` / `token_name` | 同上，用户级 |
| `gjson: messages.3.content` | 内容启发式：依赖 ZCode 固定注入 `[1][2]` 两条 reminder，改版即错位；首条输入相同的会话会撞车；长输入会撑大缓存键 |
| `gjson: messages.0.content` | 12 条完全一致（8420 字符），无法区分会话，且会把 8KB 原文拼进缓存键 |
|「同步字段」把 header 写进 body | 时序不对，亲和判定早于参数覆盖（见 §3.1） |
| `user_agent_include: ["ZCode"]` | 它只是过滤器，不产生 Key；且中间过了一层代理，UA 可能被改写 |

## 7. 可行方案

### 7.1 推荐：升级到含 `request_header` 的版本（v1.0.0-rc.7 及以上）

**当前常驻实例 `v1.0.0-rc.25` 已经满足条件，无需任何代码改动。**

实测确认其前端 bundle 中已包含：

```js
["context_int","context_string","request_header","gjson"]
["id","token_id","token_key","token_group","group","username","user_group","user_email","specific_channel_id"]
```

ZCode 的规则配置：

```json
{
  "name": "zcode by-session",
  "model_regex": ["^.*$"],
  "path_regex": ["/v1/chat/completions", "/v1/messages"],
  "user_agent_include": ["ZCode"],
  "key_sources": [
    { "type": "request_header", "key": "X-Session-Id" }
  ],
  "value_regex": "",
  "ttl_seconds": 3600,
  "skip_retry_on_failure": false,
  "include_using_group": true,
  "include_rule_name": true
}
```

要点：
- `key` 用 `X-Session-Id`（大小写不敏感）
- `user_agent_include` 可选。因流量经过 nanollm 代理，UA 是否被改写未验证，不放心可去掉，改用更精确的 `path_regex` + `model_regex` 限定
- `value_regex` 可留空；若要校验 UUID，可用 `^[0-9a-fA-F-]{36}$`
- `include_using_group` / `include_rule_name` 建议保持 `true`，便于按分组隔离、按规则名清缓存

### 7.2 备选：为 v0.11.5 自行打补丁

若必须停留在 v0.11.5，改动共 4 处（`Key` 字段现成，可复用为 header 名）：

需**编译并重新部署**才生效，纯配置无法实现。

## 9. 排查踩坑记录：nanollm 的 SQLite 记录库不完整

**现象**：`~/.nanollm/nanollm.sqlite3` 的 `records` 表只有 19 条，而服务端 `/record/summary` 返回 21 条。

| 来源 | 记录数 | source 分布 |
|---|---|---|
| `/record/summary`（服务端内存） | **21** | other 12 / claudecode 7 / **codex 2** |
| `nanollm.sqlite3` | 19 | other 12 / claudecode 7 |

**缺失的恰好是 2 条 Codex CLI 记录（`path=/v1/responses`）。** 这两条的 `createdAt` 为 23:01:22，而 SQLite 主文件 mtime 为 23:01:23.66，相差不到 1 秒。

已排除读取方式问题：用 `sqlite3` CLI 与 Python `sqlite3`（SQLite 3.45.1）读取**复制出**的库文件（含 `-wal` / `-shm`），结果均为 19 条。

**教训**：判断「nanollm 见过哪些请求」时，`records` 表不可作为唯一依据，应使用 `/record/summary` 接口。本次分析中此问题一度导致「无 Codex 流量」的错误结论。

**四类来源结论一致，无相互矛盾之处**；其中 Issue #4896 的场景（Agent 只在 header 带会话标识、同步字段无效）与 ZCode 的处境完全对应，可视为该功能正是为这类客户端补的。
